
# FIDES — Project Development Rules

## 1. Language Rules

- All source code comments must be written in English.
- All commit messages must be written in English.
- All variable, function, class, interface, type, and file names must use English.
- Technical documentation must be written in English.
- User-facing product content must follow the language specified in the product requirements.
- Communication with the project owner may use Indonesian.

## 2. Code Quality

- Follow the existing project architecture unless an approved migration plan specifies otherwise.
- Prefer readable, maintainable, modular code.
- Avoid unnecessary abstractions and premature optimization.
- Avoid duplicated business logic.
- Do not introduce dependencies without a clear technical reason.
- Use strict TypeScript typing.
- Avoid `any` unless technically necessary and documented.

## 3. Security

- Never hardcode secrets, API keys, passwords, or private keys.
- Validate and sanitize all external inputs.
- Enforce authentication and authorization on protected endpoints.
- Never expose private information through public APIs or logs.
- Follow FIDES evidence privacy and governance requirements.

## 4. Database

- Use Prisma for database access and migrations.
- Never execute destructive migrations without explicit approval.
- Preserve existing data.
- Keep schema changes consistent with migration files.

## 5. Git and Commits

- All commit messages must be written in English.
- Use clear, descriptive commit messages.
- Prefer Conventional Commits where appropriate.
- Never include AI attribution in commit messages.
- Never include phrases such as:
  - `Written by AI`
  - `Generated by AI`
  - `Co-authored-by: AI`
  - `Co-authored-by: Claude`
  - `Assisted by ChatGPT`
  - `Generated with Claude Code`
  - Any equivalent AI-related attribution or signature.
- Do not add AI-related trailers, signatures, or metadata to commits.
- Do not add AI attribution to source code headers, comments, documentation, or generated files unless explicitly required by the project owner.
- Do not commit secrets, environment files, generated runtime data, or unnecessary artifacts.
- Never create a commit or push changes without authorization.

## 6. Testing

- Add or update tests when business logic changes.
- Test security-sensitive functionality.
- Do not claim tests have passed unless they were actually executed.
- Do not ignore failing tests without documenting the reason.

## 7. FIDES Business Rules

- Never allow token ownership to influence influencer ratings.
- AI must never independently approve or publish ratings.
- Committee decisions must follow the approved methodology.
- Preserve evidence provenance and auditability.
- Follow the approved FIDES methodology and acceptance criteria.

## 8. Development Workflow

- Follow the approved implementation plan.
- Work in small, logically separated phases.
- Do not silently expand project scope.
- Do not overwrite existing implementations without reviewing their dependencies.
- Report blockers and unresolved decisions instead of making assumptions.

- Follow the phase order in docs/FIDES-IMPLEMENTATION-PLAN.md and wait for explicit owner approval before starting each phase.

## 9. Session and Context Rules

- CLAUDE.md is loaded automatically at session start. Do not re-read it during a session unless the project owner asks or it was just modified.
- Do not invoke the caveman, ponytail, or graphify skills on your own initiative. The project owner invokes them explicitly (/caveman, /ponytail, /graphify).
- Do not run graphify or any command that writes analysis output unless the owner asks.
- Do not repeat audits already documented in docs/FIDES-IMPLEMENTATION-PLAN.md. Use the plan as the source of truth for scope and phase order.
- Do not create a new repository, remote, or fork. The project owner creates repositories. Never run git init, add remotes, or create repositories through gh.

## 10. FIDES Product Rules (approved)

- Product name: FIDES. Token: $FIDES. Never use ORDO, $MRD, agent, Dossier, BULWARK, LAUREL, or any other product name in UI, metadata, sitemap, code identifiers, or docs, except in migration notes that explain the rename.
- MVP supports X accounts only. Data models and services must stay platform-neutral (Influencer 1..n SocialAccount with a platform enum) so YouTube and Telegram can be added later.
- Rating scale AAA to D, plus modifiers, NR, Outlook, and Rating Watch, exactly as defined in docs/fides-reference/Dev-Brief-Ordo-to-FIDES.md.
- Four pillars and weights: Call Accuracy 35, Disclosure 25, Wallet Alignment 25, Conduct 15. Automatic rules (NR, default D, rug cap, transparency cap) cannot be changed by the committee.
- Human Rating Committee decides final ratings: minimum 3 non-conflicted votes, final rating within one notch of the scorecard and never above a cap, conflicted members recuse, published rationale when different from the scorecard.
- AI may draft and recommend only. No code path may let AI create votes, finalize, or publish a rating.
- Token holders get FIDES Desk benefits (data, alerts, API, tips). Token ownership must never influence any rating, score, or committee decision.
- Public data only. No private data, no wallet clustering or guessed wallets, no unverified or pending evidence in public APIs. Evidence must keep provenance (source URL, capture time, content hash, who captured it).
- Notice of 48 hours before publication, right of reply, one appeal per rating action within 14 days, Rating Watch maximum 90 days with a public reason, takedown returns 410 Gone.
- Every rating page carries the opinion disclaimer from the brief. Use "proven undisclosed", never accusatory wording such as "scammer".
- Open decisions (token mint, holder threshold, final domain, API providers, committee identities) must never be guessed. Fail closed or ask the owner.

## 11. Architecture Rules (approved)

- Frontend: Next.js (App Router), React, TypeScript, deployed on Vercel. SSR/ISR for public rating pages. No business logic in Next.js API routes.
- Backend: NestJS is the only business-logic and API layer. Prisma is the only ORM. Deployed on Railway.
- Database: Supabase PostgreSQL (and Storage for evidence). Do not add Supabase Auth; keep a single auth system (wallet sessions for members and staff; staff roles ANALYST and COMMITTEE_MEMBER come from an owner-managed wallet allowlist in server config, never from token ownership). Enable RLS with no public policies.
- Queues: BullMQ + Redis on Railway. The indexer is a future separate service; do not build it unless the owner approves.
- Provider access (X, prices) goes through adapter interfaces. Post and price data use analyst manual input in the MVP. Profile claims use X OAuth login (owner-provided X API credentials in environment variables only, with a spending limit set in the X Developer Console); there is no bio-code step.
- Keep the architecture decisions in docs/FIDES-IMPLEMENTATION-PLAN.md. Do not change the stack without a written technical reason and owner approval.

## 12. Free-Plan Cost Rules (Supabase and Railway)

- Keep database size small: no raw post bodies, HTML, or large JSON in Postgres; store evidence files in Storage and only hash, URL, and path in the database; prune ephemeral tables (nonces, expired sessions, old logs) on a schedule; add indexes only for real queries.
- Keep egress low: paginate all lists, use Prisma select, return summaries on list endpoints, cache public responses (ISR and Cache-Control), serve evidence only through short-lived signed URLs to staff.
- Browsers must never connect to Supabase directly.
- Use the pooled connection URL at runtime with a small Prisma pool, and the direct URL only for migrations.
- Railway MVP runs API and worker in one service (ROLE switch allows a later split). Use the smallest Redis, small job payloads, removeOnComplete and removeOnFail limits.
- Do not add services, scheduled jobs, or dependencies that increase continuous resource usage without owner approval.

## 13. Security and Environment Rules (additions)

- Never commit .env files, dump.rdb, dev.db, key material, or seed output that contains staff keys.
- CORS must use an explicit allowlist in production. Production must refuse to boot with missing CORS_ORIGINS, a NOTICE_HOURS below 48, or SEED_DEMO=true.
- Staff and committee endpoints always require authentication and role checks. Log staff actions in the audit table.
- Do not run destructive scripts (for example wipe-database.ts) and never run migrations against any database other than the one the owner names.
- Remote (staging/production) deployment, database changes, and secret changes require explicit owner approval each time.

## 14. Testing and Language (additions)

- Public API leakage tests (votes, staff identities, member wallets, tip senders, pending evidence, removed accounts) are required for any change to public endpoints.
- Rating-engine, quorum, notice, appeal, watch, and takedown rules each need an automated test before the related phase is considered done.
- Report test results exactly as executed. State which phases were not tested.
- Code, comments, commits, and documentation in English. Reports to the owner may be in Indonesian.
